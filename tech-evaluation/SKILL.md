# 技术评估文档编写

协助用户编写高质量的技术选型与评估文档。核心流程：先确认目标与范围，再动态组装文档结构，
最后按模块引导完成内容。

## 工作流

### 1. 目标确认（必需）

在开始写作前，通过对话与用户确认以下信息，根据回答裁剪后续结构：

- **评估对象**：框架？库？语言？基础设施？AI 模型？
- **技术域**：前端 / 后端 / 移动端 / 基础设施 / 数据 / AI / 跨端 / 通用架构
- **受众**：技术团队内部评审 / 架构委员会 / 管理层（影响详略与措辞）
- **约束条件**：时间线、预算上限、必须兼容的存量系统、团队规模
- **已有候选方案**：用户是否已有倾向，还是需要从零筛选
- **是否已做 PoC/ benchmark**：有数据 vs 纯桌面研究，写作策略不同

### 2. 维度筛选

基于确认结果，从 [references/dimensions.md](references/dimensions.md) 中选择相关维度，
剔除无关项（如纯前端选型无需考虑数据库一致性模型）。向用户展示拟采用的维度列表并确认。

### 3. 结构组装

使用 [references/templates.md](references/templates.md) 中的文档模板，结合已选维度生成定制化大纲。
大纲必须包含：

- TL;DR / 执行摘要（放在最前）
- 背景与约束
- 候选方案纵向研究（每方案一个章节）
- 横向对比（决策矩阵表）
- 风险评估
- 建议与回滚方案

可选但强烈推荐的章节：

- **关键问题与推荐方案**：横向对比中暴露的棘手矛盾点（如认证态隔离、AI 非确定性、存量迁移冲突），单独成节并给出具体解决思路与配置示例

如果用户只需要某一部分（如只写横向对比），则仅输出该部分。

### 4. 内容编写

按组装后的大纲逐章引导：

- 每章先确认用户已有素材，再组织成文
- 优先使用用户提供的数据、截图、PoC 结果
- 缺乏数据时，明确标注"待补充"或基于公开信息给出引用
- 语言遵循 templates.md 中的风格指南

### 5. 质量检查

文档初稿完成后，对照 [references/templates.md](references/templates.md) 中的质量检查清单逐项校验，
向用户报告通过项与待改进项。

## 核心原则

- **结构 > 文采**：技术文档的价值在于降低决策不确定性，优先保证逻辑清晰
- **具体 > 抽象**：用数据、场景、代码示例替代"性能好""生态丰富"等模糊描述
- **可裁剪 > 全量**：不强行输出无关维度，宁缺毋滥
- **人类第一**：排版为人类阅读优化，AI 可读是副产品而非目标
- **结论前置**：TL;DR 放在开头，细节支撑放在后面
